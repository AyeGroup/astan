# معماری سیستم

## ۱. جریان یک نوبت گفتگو

```
پیام کاربر
    │
    ▼
Sanitizer ─────────── رمز/کد ملی/توکن Mask می‌شود و شمارش می‌شود
    │
    ▼
Intent Detection ──── قاعده‌محور و قطعی، بدون رفت‌وبرگشت به مدل
    │
    ▼
Reconcile with Page ─ اگر صفحه با مرحله ثبت‌شده نخواند، صفحه برنده است
    │
    ▼
Rule Answer ───────── پاسخ Grounded از Workflow + Knowledge Base
    │
    ▼
LLM Rephrase ──────── اختیاری؛ Baseline را روان‌تر می‌کند (نه عوض)
    │
    ▼
Policy Enforcement ── هر Action دوباره Parse و اعتبارسنجی می‌شود
    │
    ▼
Response Contract ─── message + workflow + actions + quick_actions
```

نکته کلیدی ترتیب مراحل است: `Rule Answer` **قبل** از مدل اجرا می‌شود. اگر بعد
از آن بود، فقط یک Fallback بود؛ چون قبل از آن است، هم منبع Grounding مدل است و
هم معیار سنجش خروجی آن.

## ۲. State Machine

هر Workflow یک گراف از Stepهاست. هر Step این‌ها را اعلام می‌کند:

- `expected_pages` — کاربر برای این مرحله باید کجا باشد.
- `allowed_targets` — دستیار در این مرحله اجازه اشاره به چه عناصری دارد.
- `primary_target` — اولین چیزی که Highlight می‌شود.
- `transitions` — کدام رویداد به کدام مرحله می‌برد.
- `error_events` — چه خطاهایی اینجا مشروع‌اند.

انتقال فقط با رویدادِ اعلام‌شده انجام می‌شود. رویدادی که در جدول انتقال مرحله
فعلی نباشد **نادیده گرفته می‌شود**، نه اینکه حدس زده شود؛ در غیر این صورت یک
رویداد تکراری یا Replayشده کاربر را به مرحله اشتباه پرتاب می‌کرد.

### Reconciliation

اگر کاربر دکمه Back مرورگر را بزند یا نشستش منقضی شود، وضعیت ثبت‌شده دیگر
درست نیست. `reconcileWithPage` صفحه را به‌عنوان مرجع حقیقت می‌گیرد و مرحله را
به Stepی می‌برد که آن صفحه را انتظار دارد.

## ۳. لایه‌های امنیتی Action

یک Action باید از چهار دروازه رد شود:

1. **واژگان** — `ActionSchema` یک Discriminated Union است. چیزی مثل
   `execute_javascript` اصلاً Parse نمی‌شود، چون عضوی از این نوع نیست.
2. **سیاست مرحله** — هدف باید در `allowed_targets` مرحله فعلی باشد.
3. **واقعیت صفحه** — هدف باید در `present_targets` هم باشد؛ یعنی سایت واقعاً
   آن عنصر را رندر کرده است. اشتراک این دو مهم است: مرحله OTP ممکن است
   `otp_resend` را مجاز بداند، اما اگر سایت دکمه ارسال مجدد را نساخته باشد،
   نباید به فضای خالی اشاره کنیم.
4. **تأیید کاربر** — عملیات ممتاز (مثل `RESEND_OTP`) همیشه `requires_confirmation`
   می‌گیرند، حتی اگر مدل خلافش را بخواهد.

در سمت مرورگر هم `resolveTarget` دوباره بررسی می‌کند که عنصر واقعاً وجود دارد و
دیده می‌شود — چون بین ارسال Context و رسیدن پاسخ، صفحه ممکن است عوض شده باشد.

### چرا عنصر باید Tag شده باشد

SDK فقط عناصری را می‌بیند که توسعه‌دهنده سایت با `data-assistant-target` علامت
زده باشد. یک `input[type=password]` که هرگز Tag نشده، از دید دستیار **وجود
ندارد**. حتی اگر اشتباهاً Tag شود، `registry.ts` نوع `password` و `hidden` را
رد می‌کند.

## ۴. عملیات ممتاز

```
دستیار: «می‌خواهید رمز دوباره ارسال شود؟»
   │
   ▼ (کاربر تأیید می‌کند)
SDK ──▶ options.onOperationRequest('RESEND_OTP')
   │
   ▼
سایت قواعد خودش را اعمال می‌کند (مثلاً محدودیت ۳۰ ثانیه)
   │
   ▼
POST /assistant/operation { allowed: false, reason: … }
   │
   ▼
دستیار فقط نتیجه را به کاربر می‌گوید
```

دستیار هیچ مسیری به سرویس OTP ندارد. تنها چیزی که می‌داند، همان بولینی است که
سایت برگردانده.

## ۵. مدل نشست

نشست دستیار عمداً ناشناس است: مرحله، رویداد آخر، شمارش شکست، و یک تاریخچه
کوتاه گفتگو. نه کد ملی، نه شماره تلفن، نه توکن. نشتِ کامل این Store هیچ چیزی
درباره یک شهروند فاش نمی‌کند.

## ۶. رفتار در نبود مدل

| شرایط | رفتار |
|---|---|
| `ANTHROPIC_API_KEY` تنظیم نشده | `source: "rules"` — پاسخ کامل قاعده‌محور |
| خطای API یا Timeout | `source: "llm_fallback_rules"` |
| مدل Refuse کند | `source: "llm_fallback_rules"` |
| پاسخ مدل Action نامعتبر داشته باشد | Action حذف می‌شود، متن می‌ماند |

در هر چهار حالت، کاربر یک پاسخ درست و یک راهنمایی بصری می‌گیرد.

## ۷. سنجه‌ها

`GET /assistant/analytics` سنجه‌های سند §32 را برمی‌گرداند: نرخ شروع و تکمیل
فرآیند، Drop-off، مراحل پرخطا، Intentهای پرتکرار، نسبت پاسخ‌های Grounded، تعداد
Actionهای ردشده به تفکیک دلیل، و تعداد Maskشدن داده حساس. سنجه‌ها Aggregate
هستند و هیچ محتوای گفتگویی در آن‌ها ذخیره نمی‌شود.
