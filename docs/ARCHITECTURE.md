# معماری پلتفرم راهنمای هوشمند موزه

سندی برای تصمیم‌های فنی، قرارداد API و نقشهٔ راه. مخاطبش تیم فنی است.

---

## ۱. تصمیم بنیادی: رندر روی دستگاه بازدیدکننده

سه معماری برای آواتار سخنگو ممکن بود:

| رویکرد | تأخیر | هزینهٔ متغیر هر بازدید | وابستگی خارجی |
|---|---|---|---|
| API ابری (HeyGen / D-ID / Simli) | ۱ تا ۲ ثانیه | دقیقه‌ای، پرداختی | بالا، ریسک تحریم |
| GPU سلف‌هاست (MuseTalk / Wav2Lip) | ۱ تا ۲ ثانیه | استهلاک GPU | ندارد |
| **رندر دوبعدی روی مرورگر (انتخاب‌شده)** | زیر ۵۰ میلی‌ثانیه | **صفر** | ندارد |

انتخاب سوم یعنی موزه با یک بازدیدکننده و با ده‌هزار بازدیدکننده **دقیقاً یک
هزینه** دارد. برای مدل درآمدی اشتراکی این تفاوت تعیین‌کننده است: حاشیهٔ سود با
رشد مصرف کم نمی‌شود.

بهایش واقع‌گرایی کمتر چهره است. برای سناریوی «QR کنار ویترین، گوشی در دست، سی
ثانیه تعامل» این معامله به‌صرفه است؛ برای یک توتم دو متری در ورودی موزه ممکن
است نباشد — به بخش نقشهٔ راه نگاه کنید.

## ۲. جریان داده

```
QR کنار اثر
   │  ?bot=<uuid>&obj=<objectId>&t=<عنوان>&av=<avatar>&lang=fa
   ▼
viewer.html ──► RagClient ──► ragbuilder (SSE یا JSON)
   │                              │
   │                     ┌────────┘  پاسخ به‌صورت جریانی
   │                     ▼
   │              SentenceQueue        جمله‌به‌جمله، نه یک‌جا
   │                     │
   │                     ▼
   │               Speaker (TTS)  ──► AudioBuffer ──► AnalyserNode
   │                                                      │
   │                                            RMS و مرکز طیفی
   │                                                      ▼
   └──────────────────────────────────────────► AvatarRenderer (warp)
```

شناسهٔ اثر به‌عنوان `context` در payload تزریق می‌شود، بنابراین پرسش
«این اثر چیست؟» بدون آنکه بازدیدکننده نام اثر را بداند پاسخ می‌گیرد. این تنها
جایی است که QR ارزش واقعی می‌سازد و صرفاً یک لینک نیست.

## ۳. بودجهٔ تأخیر و مهم‌ترین اهرم

تأخیر ادراکی، فاصله تا **اولین کلمهٔ صوتی** است، نه تا پایان پاسخ:

| مرحله | بودجه |
|---|---|
| تشخیص گفتار (پس از پایان صحبت) | ۲۰۰ تا ۴۰۰ میلی‌ثانیه |
| اولین جملهٔ کامل از RAG | ۴۰۰ تا ۹۰۰ میلی‌ثانیه |
| سنتز گفتار جملهٔ اول | ۲۰۰ تا ۴۰۰ میلی‌ثانیه |
| شروع لب‌سینک | زیر ۵۰ میلی‌ثانیه |
| **مجموع** | **حدود ۱ تا ۱٫۷ ثانیه** |

مهم‌ترین اهرم، `SentenceQueue` است. اگر منتظر کامل شدن پاسخ بمانیم، تأخیر به
سه تا پنج ثانیه می‌رسد و تجربه می‌شکند. با پخش جملهٔ اول، بقیهٔ تولید مدل زیر
صدای آواتار پنهان می‌شود.

**پیش‌نیاز:** endpoint سرویس RAG باید استریم (SSE) بدهد. اگر ندهد، این اهرم از
دست می‌رود و باید در سمت ragbuilder اضافه شود. مهم‌ترین قلم فنی است که باید
تأیید شود.

## ۴. لایهٔ صوت: محدودیت واقعی

دو محدودیت که باید در تصمیم‌گیری لحاظ شوند، نه در زمان تست کشف شوند:

**یک.** خروجی `speechSynthesis` مرورگر قابل اتصال به WebAudio نیست. یعنی در
حالت TTS مرورگری، سیگنالی برای تحلیل وجود ندارد و لب‌سینک از یک پوش هجایی
مصنوعی تغذیه می‌شود که «شبیه حرف زدن» است ولی با واج‌ها هم‌گام نیست.
لب‌سینک واقعاً هم‌گام فقط با TTS سمت سرور به دست می‌آید.

**دو.** پوشش صدای فارسی در مرورگرها ضعیف است. روی iOS Safari عملاً صدای فارسی
وجود ندارد و روی اندروید تضمینی نیست. با توجه به اینکه سناریوی انتخابی موبایل
است، **TTS سمت سرور یک انتخاب نیست، یک الزام است.**

پیشنهاد مشخص: **Piper** با صدای `fa_IR`. روی CPU اجرا می‌شود، سریع‌تر از
بی‌درنگ است، سلف‌هاست و بدون وابستگی خارجی. یک سرویس کوچک که متن می‌گیرد و
`audio/mpeg` برمی‌گرداند کافی است؛ `tts.endpoint` را به آن بدهید.

برای تشخیص گفتار هم مسیر پایدار، `faster-whisper` (مدل `large-v3`) روی سرور
است. `webkitSpeechRecognition` فقط به‌عنوان مسیر سریع اندروید نگه داشته شده.

## ۵. کش: اهرم دوم هزینه و تأخیر

در یک موزه، اکثریت قاطع پرسش‌ها تکراری‌اند. صوت سنتزشده با کلید SHA-256 از
(متن + صدا + سرعت) در IndexedDB کش می‌شود، پس پاسخ‌های پرتکرار برای همان
دستگاه آنی پخش می‌شوند.

قدم بعدی که ارزش بیشتری دارد: **پیش‌رندر سمت سرور**. بیست پرسش پرتکرار هر اثر
را شبانه سنتز کنید و به‌صورت فایل ثابت سرو کنید. با شباهت برداری پرسش، پاسخ
آماده برگردانده می‌شود؛ تأخیر عملاً صفر و بار TTS نزدیک صفر.

## ۶. قرارداد API که باید تأیید شود

`app/js/config.js` بخش `rag` بر اساس ویجت فعلی حدس زده شده و **تأیید نشده**
است، چون از محیط توسعه دسترسی شبکه به `ragbuilder.aia-ai.com` وجود نداشت.
تا زمان تأیید، `transport: 'auto'` در صورت خطا به دادهٔ نمایشی برمی‌گردد تا
دمو همیشه قابل ارائه باشد.

اقلامی که باید تأیید شوند:

1. مسیر دقیق endpoint گفت‌وگو (فرض فعلی: `POST {baseUrl}/chat`).
2. نام فیلدهای payload: `message` / `bot_uuid` / `session_id`.
3. آیا SSE پشتیبانی می‌شود؟ اگر بله، شکل هر event چیست؟
4. آیا فیلد `context` برای محدودکردن بازیابی به یک اثر پذیرفته می‌شود؟
   اگر نه، جایگزین: تزریق عنوان اثر به ابتدای پرسش.
5. سیاست CORS برای دامنهٔ استقرار موزه.

پس از تأیید، فقط `config.js` تغییر می‌کند؛ هیچ لایهٔ دیگری دست نمی‌خورد.

## ۷. استقرار

خروجی کاملاً ایستا است: بدون فرآیند build، بدون وابستگی npm، بدون CDN.
هر وب‌سروری کافی است.

```
app/viewer.html   صفحهٔ بازدیدکننده (مقصد QR)
app/studio.html   استودیوی کالیبراسیون آواتار
index.html        صفحهٔ فرود و ابزار ساخت لینک اثر
tools/make_qr.py  تولید انبوه QR از روی CSV آثار
```

پیکربندی هر موزه با یک بلوک پیش از اسکریپت انجام می‌شود:

```html
<script>
  window.MUSEUM_CONFIG = {
    rag: { baseUrl: 'https://ragbuilder.aia-ai.com/api/public', botUUID: '...' },
    tts: { mode: 'server', endpoint: 'https://tts.example.com/speak' },
    stt: { mode: 'server', endpoint: 'https://stt.example.com/transcribe' },
    analytics: { endpoint: 'https://api.example.com/events' }
  };
</script>
```

نکته: فونت و تمام دارایی‌ها محلی‌اند. صفحه داخل ساختمانی با شبکهٔ فیلترشده یا
کندی شدید هم بالا می‌آید.

## ۸. آنچه ساخته شده و آنچه نشده

**ساخته شده:** موتور لب‌سینک، پایپ‌لاین جریانی، صفحهٔ بازدیدکننده، استودیوی
کالیبراسیون، آداپتور RAG، سه‌زبانه، کش صوت، ابزار ساخت لینک و QR.

**ساخته نشده:**

- پنل ادمین چندمستأجری (ایجاد موزه، آپلود محتوا، مدیریت آثار). بخش بارگذاری
  محتوا و ساخت بات همین حالا در ragbuilder موجود است؛ آنچه کم است لایهٔ
  مدیریت آثار و اتصالشان به بات است.
- سرویس TTS و STT. طراحی شده و قرارداد مشخص است، ولی استقرار نشده.
- داشبورد تحلیل. رویدادها ارسال می‌شوند؛ مصرف‌کننده‌شان ساخته نشده.
- تشخیص چهره برای کالیبراسیون خودکار خط لب. فعلاً یک کلیک اپراتور است.

## ۹. نقشهٔ راه پیشنهادی

**فاز یک — قابل فروش (۱ تا ۲ هفته)**
تأیید قرارداد API، استقرار Piper و Whisper، اجرای پایلوت روی ده اثر یک موزه.
اینجا نقطه‌ای است که می‌توان دمو را جلوی مشتری برد.

**فاز دو — عملیاتی (۳ تا ۴ هفته)**
پنل ادمین آثار، داشبورد «بیست پرسش پرتکرار هر اثر» (گزارشی که موزه بابتش پول
می‌دهد، چون به چیدمان و برچسب‌گذاری‌اش جهت می‌دهد)، پیش‌رندر پاسخ‌های پرتکرار.

**فاز سه — تمایز**
افزودن مسیر GPU سلف‌هاست برای توتم‌های ورودی موزه، جایی که کیفیت چهره واقعاً
دیده می‌شود. معماری از ابتدا مستقل از موتور رندر نوشته شده، پس این افزودن است
نه بازنویسی.
