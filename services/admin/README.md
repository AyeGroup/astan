# پنل مدیریت و داشبورد پرسش‌ها

سرویسی مستقل کنار ragbuilder. ragbuilder خودش بارگذاری محتوا و خود بات را
دارد؛ آنچه کم بود لایه‌ای است که می‌داند هر QR به کدام **اثر فیزیکی** اشاره
می‌کند، و بازدیدکننده مقابل آن اثر واقعاً چه پرسیده است.

## چرا SQLite

کل بار کاری یک نوشتن به‌ازای هر پرسش بازدیدکننده است و چند خواندن گروه‌بندی‌شده
برای هر بار دیدن داشبورد. این سال‌ها در یک فایل با WAL جا می‌شود و یک سرویس را
از دوش تیم فنی موزه برمی‌دارد. مهاجرت به Postgres بعداً کار یک روز است؛ اجرای
Postgres از روز اول هزینه‌ای است که هر استقرار می‌پردازد.

## مسئلهٔ واقعی: گروه‌بندی پرسش‌ها

گزارشی که موزه بابتش پول می‌دهد «بیست پرسش پرتکرار هر اثر» است. گروه‌بندی
رشتهٔ خام آن را نمی‌سازد: «چایخانه کجاست؟» و «کجاست چای‌خانه» یک پرسش‌اند و
در دو ردیف می‌افتند، پس پرتکرارترین پرسش تکه‌تکه می‌شود و اصلاً بالا نمی‌آید.

Embedding حلش می‌کند ولی یک مدل، یک پایگاه برداری و یک رفت‌وبرگشت شبکه به چیزی
اضافه می‌کند که در غیر این صورت یک سرویس کوچک SQLite است. یک **اثر انگشت
ریخت‌شناختی** بیشتر راه را برای فارسی بدون هیچ زیرساختی می‌رود:

```
نرمال‌سازی → حذف کلمات دستوری → حذف پسوند → مرتب‌سازی → اتصال
```

دو تصمیم عمدی در این خط لوله:

**کلمات پرسشی حذف نمی‌شوند.** «کجا»، «چند»، «چرا» و «چیست» تمام معنای پرسش را
حمل می‌کنند — «قیمت چند است» و «قیمت کجاست» دو پرسش متفاوت‌اند و نباید ادغام
شوند. در عوض یکسان‌سازی می‌شوند، چون «کجاست» همان «کجا» است با فعل ربطی چسبیده.

**ریشه‌یابی فقط پسوندی و محافظه‌کارانه است.** ریشه‌یابی سبکی که دنبال پیشوند هم
برود کلمات بی‌ربط را ادغام می‌کند، و یک ادغام غلط در این گزارش بدتر از یک ادغام
از دست رفته است: موزه بر اساسش تصمیم می‌گیرد.

**محدودیت شناخته‌شده:** فاصله‌گذاری کلمات مرکب حل نشده — «چای خانه» با فاصله از
«چایخانه» جدا می‌ماند. تنظیم بیشتر برای پوشاندنش ریسک ادغام غلط داشت.

## معیارهایی که واقعاً به کار موزه می‌آیند

| گزارش | چه تصمیمی می‌سازد |
|---|---|
| پرتکرارترین پرسش‌ها | چه چیزی باید روی برچسب ویترین نوشته شود |
| پرسش‌های بی‌پاسخ‌مانده | کجای محتوای موزه خالی است |
| پربازدیدترین آثار | کدام ویترین بیشترین کنجکاوی را می‌سازد |
| زبان بازدیدکنندگان | آیا سرمایه‌گذاری روی انگلیسی و عربی توجیه دارد |
| ساعات پرسش | نیروی راهنما کی لازم است |
| تأخیر تا اولین کلمه | سلامت عملیاتی سرویس |

«پرسش‌های بی‌پاسخ‌مانده» پرسش‌هایی است که بازدیدکننده ظرف سی ثانیه دوباره چیز
دیگری پرسیده. کسی که بلافاصله دوباره می‌پرسد معمولاً چیزی را که می‌خواست نگرفته.
این معیار **هیچ سیگنال اضافه‌ای از کلاینت نمی‌خواهد** و دقیقاً به همین دلیل
اصلاً کار می‌کند.

## اجرا

```bash
pip install -r requirements.txt
ADMIN_TOKEN=secret VIEWER_URL=https://museum.example.com/app/viewer.html \
  uvicorn app.main:app --port 8082
```

یا `docker compose up -d`. پنل روی `/` بالا می‌آید.

## API

| مسیر | دسترسی | کار |
|---|---|---|
| `POST /events` | عمومی | ورودی رویداد از صفحهٔ بازدیدکننده |
| `GET /api/museums` | توکن | فهرست موزه‌ها |
| `POST /api/museums` | توکن | ساخت موزه |
| `GET /api/museums/{slug}/objects` | توکن | آثار به‌همراه لینک QR آماده |
| `PUT /api/museums/{slug}/objects/{code}` | توکن | افزودن یا ویرایش اثر |
| `DELETE /api/museums/{slug}/objects/{code}` | توکن | حذف اثر |
| `GET /api/museums/{slug}/qr.csv` | توکن | CSV آمادهٔ `tools/make_qr.py` |
| `GET /api/museums/{slug}/dashboard` | توکن | همهٔ گزارش‌ها |

`POST /events` عمداً عمومی است، چون از مرورگر بازدیدکننده صدا زده می‌شود. بات
ناشناخته `204` می‌گیرد نه `404` — این endpoint از هر مرورگری قابل دسترسی است و
`404` تأیید می‌کرد کدام شناسه‌های بات واقعی‌اند.

## اتصال به صفحهٔ بازدیدکننده

هیچ تغییری در کلاینت لازم نیست؛ همان payload که `app/js/viewer.js` الان
می‌فرستد پذیرفته می‌شود. فقط مقصد را بدهید:

```html
<script>
  window.MUSEUM_CONFIG = {
    analytics: { enabled: true, endpoint: 'https://admin.example.com/events' }
  };
</script>
```

## پیکربندی

| متغیر | پیش‌فرض | کار |
|---|---|---|
| `ADMIN_DB` | `./data/museum.sqlite3` | مسیر فایل SQLite |
| `ADMIN_TOKEN` | خالی | نگهبان مسیرهای `/api`. خالی یعنی **باز** |
| `VIEWER_URL` | `https://museum.example.com/...` | برای ساخت لینک QR هر اثر |
| `ADMIN_CORS` | `*` | مبدأهای مجاز |
| `ADMIN_DEFAULT_DAYS` | `30` | بازهٔ پیش‌فرض داشبورد |

## تست

```bash
python3 -m pytest tests/ -q
```

دو لایه: گروه‌بندی پرسش (شامل مواردی که **نباید** ادغام شوند) و قرارداد HTTP
به‌همراه پرس‌وجوهای داشبورد.
